# D5 errata

Corrections to the design documents found while building (append only, one line per correction, newest last).
MAME wins over the design text; the design documents themselves are not edited.

- D4d s2 (boot skip): "press at 100: both screens end at 226" is wrong for text 1. A press at probe frame 100 ends the wait of text 1 early (text 2 starts at once), but text 2 still shows its full 30 + 91 frames from its early start, so the boot ends 121 frames after text 2 starts (video frame 102) and the layer control change comes 3 frames later, at video frame 226. Text 2 is only skipped by a press after its first 30 frames (boot-skip-b). M1-03.
- D4d s2, s3.2, s13 A2: frame numbers of the probe batches are video frames; a record of the harness traces is video frame - 2, and a press of a probe line `f` is seen one frame earlier by a task than the harness script line `f` (the same press gives the layer control change 0x18D6 at video frame 226 / 234 in the probe and at record 224 / 231 with `98-101:A` / `228-231:2J`). M1-03.
- D4d s4.5 and F35 (G.$4F6): the counter feeds nothing. The system task clears it (0x1827A with G.$4CC set) in the pass that creates the game task, two frames before the game start code 0x17F8A reads it, so the starting rank band is always 0; and with the factory settings (three chutes, credits per player) it never counts, because it only runs while the common pool G.$46A or free play G.$46B is not 0. M1-04.
- D4d s3.2 (attract timeline): the lengths of the profile cards (1399 frames the first time, 1407 afterwards), of the title entry and of the ranking (422 then 423) are not constant; the whole loop is 13104 frames only on average. The measured lengths are in `attract.rs` and `TITLE_RUNS` in `boot.rs`. M1-04.

- D4d s3.4 and D5 M1-05 (scroll helper): "the helper 0x9AC86 moves the checker board (scroll2 X += 4 or 8, scroll3 X += 4)" is wrong, and 0x9AC86 / 0x9ACBA are code, not tables. Both helpers act only when G.-$7014 or G.-$7012 is not 0, and no code in the ROM ever sets them (their only other uses are the clears at 0x9A818 and 0x9A832), so they do nothing. The board moves by the pool B class 94 object (scroll3 Y, G.$7E8, minus 2 per update for 295 updates of each card; MAME: 65534, 65532 ... 64946); scroll2 and scroll3 X stay 0. M1-05.
- D4d s3.4, s15 item 1 and D5 M1-06 (the card objects): pool A class 100 variants 0 to 3 are the big portrait of the hero (an animation of the table 0x71F9E, OBJ palette 16 loaded from 0xBB252 / 0xBB3B2 / 0xBB292 / 0xBB3F2, X camera + 0x58, Mess + 0x50), variants 4 to 7 are the small hero who does the moves (X camera + 0x120, Y + 0x20). Their sounds are the `+$2D` byte of the animation frames, queued in every update the frame is shown. Pool B class 93 is the checker board (a tile writer for scroll3 that also touches the last 8 cells of scroll2; its first update clears scroll3 twice and so crosses a video frame boundary), class 94 the scroll of it. Class 100 lives 300 updates and class 94 lives 296 (class 93 never frees itself); the counter of the routine stops while a fade or the clear sleeps, so every card shows its objects the whole time. M1-06.
- D4d s3.4 (timing): the first profile run is one frame ahead of the later runs at 8 places (the first pass, the pass of counter 11, and for each of the cards 2 to 4 the end of the clear sleep and the second step of the fade in), which is the 8 frames between 1399 and 1407. The two timings are in `flow/profiles.rs`. The scroll registers of the hardware show the shadow G.$7E8 two frames late in the recording (cpsa 0x16: 0x700 minus the shadow of two records before), so a port picture that shows the shadow at once has the checker 4 pixels (2 frames at 2 pixels) away from the MAME picture while it scrolls. M1-05 and M1-06.
- D4d s3.5 (ranking objects): the routine creates more objects than the Cadillac. The set-up creates, before the pools are used, a cloud manager (pool B class 89, 0x8C982, made by 0x8C96C) that makes the 15 clouds of the start (pool C class 0x80, handler 0x96A7E, speeds 3.5, 2.5 and 1.5 pixels a frame to the right of the world, i.e. slower than the 8 pixel scroll) and then, every 0 to 15 frames by a random number, one new cloud 0x280 right of the camera at one of 3 x 8 heights. The Cadillac (pool B class 86) makes two heroes (pool A class 17, 0x423A4) that follow it and bob by one random number each a frame. So the ranking screen uses the random number generator on every frame (about 3 calls), and G.$14 after it is part of the timeline. M1-07.
- D4d s3.5 (ranking timing): the states 0 and 2 are one pass (the draw), G.$7018 = 0x1A4 counts down in 421 more passes to -1 (the 422nd pass sets state 6 and returns before the objects), the scroll steps (+8 scroll2, +4 scroll3) come after the handler and before the object updates, so the Cadillac (mode 0 does not move) has moved n - 1 times after n passes. The drawing of about 2250 cells is cut by the video frame boundary in the middle of a cell write: the first frame after the call has done 3958, 3054 or 3786 of the 4498 words (code word then attribute word of each cell), by the screen before the ranking (`flow/ranking.rs`, `CUTS`). The first run is again one frame ahead of the later ones (its second pass is in the frame of the first). M1-07.

## From M1-10 and M1-11 (opening movie, the jungle and the logo, 2026-10-13)

- D4d s3.8 (counter 600) and D5 M1-10 (objects): 0x86D2E is not a sound helper. It makes a pool B class 66 object, a caption banner (a tall font line that is printed, waits and is erased, `prop/class66.rs`), and the hunters call it with the variants 0x12 and 0x13 ("THERE THEY GO!" at record 12415). The sounds are the plain `0xA63C` calls: 0x61 (the handler, and the flock), 0xEA (0x9C76: `+$82` of every pool A object is the pool tag 4, set by 0x4C48, so the thrower's table is never read), 0x73, 0x75, 0x36, the title tune 0x88. Pool B class 32 is the black bars: a fill of scroll1 rows 1 to 34 with the opaque tile 0x18 (0x81888, also called by the handler before its fade out) and a window of transparent cells (0x1F) that opens from the rows 15 and 16 outward, 9 steps of 4 frames (records 12404 to 12436). Pool B class 23 (the palette flash) and the block routines at 0x9C0AE .. 0x9C21C are not used by this movie.
- D4d s3.8 (what the objects are): pool A 11 is one hunter (two are made, `+$26` high byte 0 and 1: walk 0x14 frames, 0x8C frames, 0xC8 frames; the puff of his gun is pool A 57 variant 1, the flock is pool B 72 variant 0x600 with 7 birds eight frames apart); pool A 46 is a bird (it rises, flaps and drops feathers = pool A 48), pool A 12 a golden raptor (the variant 1 runs and makes the sound 0x73 every 8 frames, the variant 0 stands about and walks off), pool A 30 the big dinosaur of the roar (it asks for the screen shake three times with the sound 0x75, the roar 0x36 at its frame 0xC2), pool A 69 two sprite pieces of the roaring head that are put on the screen (camera X + 0xC0) for 0x50 frames (counter 1250). The random numbers: one for the place of each bird (the spawner), one in its init and five at its take-off, two at the start of a feather and one a frame after, one for each raptor, one for each caption banner, and one a pass from the counter 895 to 1120 (0x9C7F8). The movie does use `rand()` from record 12413 on, so its G.$14 is part of the check; the six injections of the ranking test are now four (the demos).
- D4d s3.8 (counter 1350): the handler sleeps 120 frames inside (0x9C694: A86), so nothing is updated and no sprite list is built for 120 frames (the last list stays on the screen). The palette helper 0x9C818 copies 17 words, one more than a palette: nine palettes of the scroll2 bank and two of the scroll3 bank, the 17th word is overwritten by the next copy (and for the last of each bank it stays).
- D4d s3.8 (end): the routine returns after the pass of the counter 0x5C8 = 1480 (record 13409, 1745 frames after its call), 30 passes after the handler of 1450 (fade out, then the clear 0xAE0, the first pass comes 3 frames after the clear starts). The frame of the last clear is missing from the pictures: the MAME picture of record 13378 shows the stale cells of scroll3 outside the window (scroll1 is cleared, scroll3 is not yet), which the renderer hides (tile codes outside 0x1C00..0x1FFF).
- Pictures (`d4d-b12/mov-fine`, every 10 frames from 12400 to 13450): 100 of 106 equal MAME. The 6 that differ (12900, 12910, 12970, 12980, 13030, 13040) are the three screen shakes of pool A 30: the displayed scroll2 Y moves by the shake offset (`screen_shake` 0x222D6 is a stub until M3-10); the request (`cam_shake(4)`) is made. ## From M1-12 and M1-13 (the demo, 2026-10-13)

- D4d s3.6 (setup): the RAM clear is done in 3 frames of CPU time and the setup, with the stage setup 0xA9BE, the map and the HUD, takes about 10 (the state byte is 0 in the records A to A + 2, the generator is 0 in A + 2 and the first game frame G.$0 = 1 is in A + 10, A = the record in which the title returned and G.$757A stepped). The generator is drawn from 0 four times before the reset to 0x1C3 (0x17F8A and the three player inits 0x4D46 ..), and a first demo and the later ones differ by one frame in the middle of the setup (`demo.rs`, module comment).
- D4d s3.6 (frame loop): the loop body is the level frame without the rank (0x186CC) and without the time limit (0x103FE, 0x1037E), and G.$602 is set by a byte write (the word is 0x0100). The loop never loses a video frame in the six rows (G.$0 counts every video frame; the 1205 video frames of D4d are the 5 frames of setup, 1201 passes and the frame the sleep needs), 100 frozen frames and 16 fade steps follow, and the routine returns 1325 frames after its call.
- D4d s3.6 (rows): the scroll controller does not start in the normal init: 0x2228A loads the event that the table 0x222B6 gives by stage and area (the rows in area 0 start at the first event, the rows in area 1 at a later event of the stage's list), sets the task state to 2 itself (so the palettes and timers of the init 0x206EA are skipped) and leaves the pointer to the next event on the loaded event. For an area that starts at X = 0 the area setup 0x207CA also draws the first screen of the area a second time at +0xBC8 (the same first block column 8 times, 256 cells at the end of scroll2).
- D4d s3.6 (input playback): 0x9A146 also writes a debug display, 4 hex digits of d0 at 0x90A000, 0x90A080, 0x90A100, 0x90A180 (scroll1 top left): FFFF in the frame a record changes, else the hero number times 4; the last hero's write stays. It is in every demo picture.
- D4d s3.6 (heroes): the three player inits (0x4D46 ..) run before the row sets the who / id word and the class of each hero, and 0x18C88 at the setup is done again by the first update of the object in mode 0 (the port relies on that).
- D4d s3.10 (coin in the demo): the call of the press start screen 0x983EE takes the system task 3 frames, so G.$4CD (set by the demo) is cleared 3 frames after the call. A start from the demo (free play) fades out the demo picture in 16 steps like any start and clears the screens in 3 stages (sprites and scroll1, scroll2 and 97 cells of scroll3, the rest of scroll3); the game task is created 18 frames after the press, G.$0 goes on counting from the demo's value.

## From M2-01 and M2-02 (settings file and system task, 2026-10-13)

- D4d s4.4 and s3.9 (prompt font): with separate chutes the prompts are not the "large 2-tile font": each player's prompt is the tall font (1 x 2 cells per letter, printer 0xE68) at 0x90A050 / 0x90A850 / 0x90B0D0: "PUSH / START BUTTON" with a credit, "INSERT COIN" without, "INSERT / ADDITIONAL COIN" with a small line `nCOIN 1CREDIT` (0x9DCC8, n = coins per credit) while coins wait; coin mode 8 adds " 2COIN START / 1COIN CONTINUE". Only the one chute modes use the big font (2 x 2 cells, 0xCE4) in the middle: INSERT ADDITIONAL COIN, PUSH START BUTTON with ONLY ONE PLAYER / UP TO TWO PLAYERS / UP TO THREE PLAYERS. The credit lines (0x9D66A) are at 0x90A0F0 / 0x90A8F0 / 0x90B0F0; the digit is a raw tile code 0 to 9 and code 0 is blank, so 0 credits show no digit. M: `flow_c-title`, `flow_c-two`, `flow_c-three-start`, `flow_system_modes`.
- D4d s4.1 and s3.10 (SERVICE): a press (not a hold or release) adds one credit to every player at any time, in a game too, and queues the coin sound 0x30 without the sound stop 0xFF00 that an accepted coin makes. Not measured (the probe has no key for it): from the code 0x9D326.
- D4d s4.1 and F36 (start edge): the start of a player is any change of its start button (G.$1A xor G.$1F at 0x9D2A2 / 0x9D2EC), so releasing the button takes the credit like pressing it did: a player who holds the start button while a credit arrives (a coin, SERVICE) starts the game when he lets go. From the code, not measured.
- D4d s4.5 (task timing): the system task loses 2 passes after the pass that creates the game task (the game task's first run takes about 3 frames of CPU time): the coin counter timer G.$46F of `flow_c-three-start` runs in 618, stands still in 619 and 620 and runs again in 621. M2-02.
- D4d s4.2 (modes other than the factory ones): MAME has no switch for them, so the checks poke G.$46B / G.$46C / G.$470 / G.$472 / G.$474 / G.$4CF at power frame 100 (`re/harness/scripts/flow_system_modes.txt`). The pictures, credits, coins, lockout bits and counter outputs equal MAME. With one chute a pass of the system task is shorter, so three records (319, 460, 462) differ by a few cells, palette words or sprites from the factory timing the port measured; see HANDOFF "M2-01 and M2-02".
